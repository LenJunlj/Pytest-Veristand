# 用例自动化方案 —— 市面主流路线对比与推荐（评审稿）

- **日期**：2026-11-07；**状态**：推荐稿（取代 `docs/Excel用例生成方案.md` 中的"Excel→代码生成"路线）
- **前提（用户确认）**：测试员写用例（Excel 规范），工程师实现自动化；VeriStand 台架自建，不再有存量 .seq
- **结论先行**：走 **V 模型标准分工**——Excel=用例规范，pytest 代码=实现（工程师写、可 AI 辅助、逐条 review），
  机械对账工具保证"用例↔代码"一一对应。**不做 Excel→代码的运行时生成**。

---

## 1. 市面主流的一个共同点（先看清）

行业里 Excel/Word 几乎**从不直接作为可执行格式**：

- 商用 HIL 平台（dSPACE AutomationDesk、Vector vTESTstudio、ETAS LABCAR、恒润 INTEWORK）能"表格化写用例"，
  是因为它们有**自己的受控表格格式 + 专有执行引擎**，不是"读 Excel 生成代码"；
- 通用自动化工具（Robot Framework / pytest / TestStand）中，Excel 的典型角色是**数据表**（参数/工况），
  或**用例规范文档**（评审与追溯），步骤逻辑由工程师用工具原生方式实现；
- "Excel 步骤表 → 生成可执行代码"属于**自制方案**，业界少见——原因正是可追溯性、可维护性与
  台架安全（生成的代码会真实写 DUT）。

> 所以"不放心"是对的：问题不在校验做得够不够，而在**不该把语义生成放进流水线**。

|---|---|---|---|---|---|

## 3. 推荐方案：规范层 / 实现层 / 对账层

```
① 规范层（测试员）: Excel 用例文档 —— 只约束结构，不约束措辞
      用例号 | 用例标题 | 步骤 | 期望结果 | 备注(评审结论/缺陷号)
      期望结果写"功能语言 + 数值"（如 硬线=0、CAN=1），不写通道/不写代码

② 实现层（工程师）: pytest 代码 —— 按现有工程规范逐条实现
      一条用例 = 一个独立 test 函数（沿用你们 2026-11-07 强制规则）
      通道一律走 bench_io/模块 channels.py（分层已落地）
      AI 可辅助起草，但**每条进 git review**；不存在"生成流水线"

③ 对账层（机械工具）: 保证 ①↔② 一一对应、期望一致、无遗漏
      tools/case_matrix.py（新，轻量）:
        输入: Excel 用例 + pytest --collect 结果
        输出: 覆盖矩阵（Excel 用例号 ↔ test 函数 ↔ 文件行号）
              缺号（有用例无实现/未启用）、多号（有实现无用例）、
              期望值不一致（Excel 期望 ≠ 代码断言常量）
      现有 tools/compare_draft.py 继续用于"有基准实现"的翻译对账
```

**为什么对账层必须机械**：测试员与工程师分开后，最大风险不是"写错"，而是"**漏实现/漏更新**"。
矩阵工具把这件事变成 CI 里一条命令，评审时一眼看到覆盖率。

## 4. 与前一稿（Excel 生成方案）的取舍

| 项目 | 前稿 | 本稿 |
|---|---|---|
| Excel 语义 | 受控词汇表（必须用注册词），驱动生成 | **自由规范文档**（只约束结构列） |
| bindings.yaml | 生成必需 | **降级为可选"措辞参照表"**（供测试员统一术语，不做强制校验） |
| 代码来源 | 生成器 | **工程师实现（AI 可辅助）**，逐条 review |
| 机械保证 | 生成器校验 | **case_matrix 对账**（覆盖/期望一致性） |
| 黑盒风险 | 有 | **无** |

## 5. 落地步骤（评审通过后）

1. **Excel 用例模板**（结构版）：列定义 + 填写示例 3 条 + 期望结果写法约定
2. **`tools/case_matrix.py`**：Excel 解析（stdlib xlsx，无新依赖）+ pytest 收集结果对比 → 矩阵报告（md/csv）
   - 用例号识别：函数名 `test_<NN>_*` 与 Excel 用例号列对齐（沿用报告序号规则）
   - 期望一致性：代码里 `assert_outputs(out, *CONST)` / `assert out[...] == v` 与 Excel 期望列比对
3. **C206-10 试点**：拿 1~2 个模块的真实 Excel 用例走一遍 ①→②→③
4. CI/日常：`pytest --collect-only -q` + `case_matrix` 合成一条"用例覆盖检查"命令

## 6. 决策点

| # | 决策 | 建议 |
|---|---|---|
| E1 | 是否采纳本稿（V 模型分工，不做生成） | 建议采纳 |
| E2 | Excel 模板是否仍保留"动作词表" | **不强制**；若你们希望术语统一，可只做"推荐用词"附录 |
| E3 | 期望值写法 | 功能语言+数值（硬线=0 / CAN=1）；判定语义默认 EQ（沿用实证） |
| E4 | 对账工具输出形态 | md（人读）+ csv（可导入 Excel）双份 |
| E5 | 是否叠加测试管理平台（方案 E） | 先不引入；等用例规模上来再评估 |

## 7. 风险与对策

| 风险 | 对策 |
|---|---|
| 测试员写的期望模糊，工程师自行解读 | 实现时澄清并回填 Excel"备注"列；对账工具标"期望不一致" |
| 用例新增但代码漏实现 | case_matrix 缺号清单进 CI/评审门 |
| 术语不统一（"三档"vs"请求三档"） | 可选术语附录（E2）；代码层不受影响 |
| 工程师实现效率 | AI 辅助起草 + 现有模板/生成器（gen_tests 用于存量 .seq 迁移仍有效） |
