## 1. 市面主流的一个共同点（先看清）

行业里 Excel/Word 几乎**从不直接作为可执行格式**：

- 商用 HIL 平台（dSPACE AutomationDesk、Vector vTESTstudio、ETAS LABCAR、恒润 INTEWORK）能"表格化写用例"，
  是因为它们有**自己的受控表格格式 + 专有执行引擎**，不是"读 Excel 生成代码"；
- 通用自动化工具（pytest / Robot / TestStand）中，Excel 的典型角色是**数据表**或**用例输入文档**，
  步骤逻辑由工程师实现；
- "Excel 步骤表 → 生成可执行代码"是自制路线，业界少见——原因是可追溯性、长期维护与
  台架安全（生成代码会真实写 DUT）。

> 当"写用例"和"实现自动化"是**同一个人**时，业界更不存在"文档→代码"的翻译环节：
> 这个人直接按工具的原生方式实现，文档只是给评审/追溯用的输入。

## 2. 六种方案对比（按"主流程度 / 与你们现状适配"）

| # | 方案 | 主流程度 | 与你们适配（同一人写用例+实现） |
|---|---|---|---|
| A | **pytest 直写 + Excel 输入清单 + 骨架/对账工具** | ⭐⭐⭐⭐⭐ 事实标准 | ✅ **推荐**：零新框架；保留全部现有资产（分层通道/Allure/锁/报告规则）；Excel 编号保证追溯 |
| B | Robot Framework 关键字驱动 | ⭐⭐⭐⭐ | ❌ 不选：其价值是"非程序员写可执行表"，同一人场景收益低，还要换报告体系 |
| C | NI TestStand 数据驱动 | ⭐⭐⭐⭐ | ❌ 不选：回到 .seq 风格、版本管理差（与你们方向相反） |
| D | 商用 HIL 测试平台 | ⭐⭐⭐⭐ | ❌ 成本高、与 NI 台架适配、锁定 |
| E | 测试管理平台 + pytest 上传结果 | ⭐⭐⭐⭐ | ➕ 追溯/报告层，可后续按需叠加，不是执行方案 |
| F | Excel 步骤表 → 生成代码（前稿） | ⭐⭐ | ❌ 黑盒生成、维护生成器、台架风险 |

## 3. 推荐方案：清单 → 骨架 → 人工实现 → 机械对账

```
① 输入清单（Excel，外部给或自写）
      用例号 | 用例标题 | 步骤(自由文字) | 期望结果 | 备注
      —— 只作为"要做什么"的规范与编号来源，不参与执行语义

② 骨架生成（工具，机械搬运，零语义）
      tools/gen_case_skeleton.py：Excel → 待实现代码骨架
      · 一条用例 = 一个空函数：test_<用例号>_<英文短名>
      · docstring 原样收录标题/步骤/期望（评审与实现时直接看）
      · 函数体只有 TODO 注释；**不生成任何通道写入/断言代码**
      · 文件头/manifest 记录"骨架来自哪个 Excel、什么时间"

③ 人工实现（同一人，AI 可辅助）
      按现有工程规范填函数体：bench_io/模块 channels 的通道 + Stimulus 方法 + EQ 断言
      通道、值域、时序全部由人决定（沿用已闭环的实证规则）

④ 机械对账（工具）
      tools/case_matrix.py：Excel 用例号 ↔ test 函数 ↔ 实现状态/期望值
      · 缺号（Excel 有用例无函数）     ← 防漏
      · 空函数（骨架未填完，TODO 仍在） ← 防半成品混入
      · 多号（有函数无用例）            ← 防私加
      · 期望值不一致（Excel 期望 ≠ 代码断言常量） ← 防漂移
      输出 md（人读）+ csv（可导入 Excel），可挂 CI
```

**为什么这样分工最省事且最安全**：同一人写用例+实现时，唯一的机械劳动是"照抄用例标题/步骤/编号"——
骨架工具干这一件事（零语义，抄错也能一眼看出）；而"写成哪条通道、写什么值、等多久"必须由人在
代码里显式决定（这些是台架事实，正是风险所在，不能交给生成器）。

## 4. 与前一稿（Excel 生成方案）的取舍

| 项目 | 前稿 | 本稿 |
|---|---|---|
| Excel 语义 | 受控词汇表，驱动生成 | **自由输入清单**（只抄标题/步骤/期望） |
| bindings.yaml | 生成必需 | **不需要**（不再有"词→通道"翻译环节） |
| 代码来源 | 生成器（语义级） | **骨架（机械级）+ 人工实现** |
| 机械保证 | 生成器校验 | **case_matrix 对账**（缺号/空函数/期望一致） |
| 黑盒风险 | 有 | **无**（生成物不含任何执行语义） |

## 5. 落地步骤（评审通过后）

1. **Excel 输入模板**（结构版，可直接用客户/内部现有表格，不强制改造）：
   必需列 = 用例号、用例标题、步骤、期望结果；其余列忽略
2. **`tools/gen_case_skeleton.py`**：stdlib 解析 xlsx（无新依赖）→ 单文件骨架
   （函数名带用例号、docstring 收录原文、TODO 占位）；支持 `--only/--skip`
3. **`tools/case_matrix.py`**：覆盖矩阵（缺号/空函数/多号/期望不一致）→ md+csv
4. **C206-10 试点**：拿 1~2 个模块真实 Excel 用例走一遍 ①→④
5. 日常：实现前跑骨架 → 实现 → `case_matrix` 绿灯 → 台架回归 → Allure 报告

## 6. 决策点

| # | 决策 | 建议 |
|---|---|---|
| E1 | 采纳本稿（Excel=输入清单，骨架+人工实现，不生成执行代码） | 建议采纳 |
| E2 | Excel 是否要求固定列 | **不强制**：只要能识别出"用例号/标题/步骤/期望"四列即可（模板提供标准版，客户表可映射） |
| E3 | 期望值写法 | 功能语言+数值（硬线=0 / CAN=1）；判定语义默认 EQ（沿用实证） |
| E4 | 对账工具输出形态 | md（人读）+ csv（可导入 Excel）双份 |
| E5 | 是否叠加测试管理平台 | 先不引入；规模上来再评估 |
| E6 | 是否需要"代码→用例文档"反向导出（供评审归档） | **可选**，后续按需：从 allure.step 文本+断言常量生成 Excel 快照 |

## 7. 风险与对策

| 风险 | 对策 |
|---|---|
| 骨架生成后长期不填完（半成品混入） | case_matrix "空函数"检查进 CI；骨架函数默认不收集（可加 `pytestmark = pytest.mark.skip` 或文件不带 test_ 前缀，人工迁入时才启用） |
| Excel 步骤描述含糊 | 同一人实现，无跨人误解；实现后在 docstring/备注回填澄清 |
| 用例号不规范 | 骨架工具要求用例号可解析（数字或"模块-序号"）；不可解析时拒绝并列出 |
| 后续想自动化更多 | 复杂批量场景再评估 Robot（B）或生成器（F），当前不需要 |

> 骨架文件建议**不带 `test_` 前缀**放 `reports/case_skeleton/`（与现有草稿惯例一致），
> 人工填完后重命名迁入 `tests/` —— 天然避免"半成品被 pytest 收集"。
